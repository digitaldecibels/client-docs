# Documentation rules

These apply to every client-docs command. The other skills describe *what* to
do; this describes what is and is not allowed while doing it.

## Documentation describes the real implementation

**Never invent** credentials, URLs, API keys, deployment procedures,
infrastructure, features, integrations, database behaviour, or client
procedures. Not as a placeholder, not as an example, not "for now".

A confidently wrong client handoff is worse than an incomplete one. The client
acts on it, and nobody finds out until the action fails.

When something cannot be verified from the repository, write:

```
**REQUIRES CONFIRMATION**: <what is unknown, and what would answer it>
```

Then add it to `requires_confirmation` in the manifest so `/docs-confirm` can
pick it up. Flagging into the void does not count.

## The evidence hierarchy

When sources disagree, the higher one wins:

1. Source code
2. Configuration files
3. Dependency manifests
4. Infrastructure configuration
5. Tests
6. Git history
7. Existing documentation
8. Comments
9. Inference

**Existing documentation does not override source code.** It is evidence about
what someone once believed, which is not the same as what the code does. A
README saying the site deploys via FTP, next to a GitHub Actions workflow that
deploys to Pantheon, means the README is wrong.

## Labelling

Every non-obvious claim is one of three things, and the reader needs to know
which:

| Label | Means |
| --- | --- |
| **Verified** | Directly supported by a file you read. Name the file. |
| **Inferred** | Reasonable from the evidence but not proven. Say what it rests on. |
| **REQUIRES CONFIRMATION** | Cannot be determined from the repository. |

If you are uncertain which applies, it is not verified.

## Secrets

Document that a secret exists, what it is for, and where it is configured.
Never its value, and never a plausible-looking fake.

```
SENDGRID_API_KEY
Purpose: transactional email
Value:   configured outside the repository
```

This holds even when the value is sitting in a `.env` file you can read. A
value read from an ignored file is still a secret, and documentation gets
committed, shared and emailed.

## Protecting hand-written content

Someone wrote the existing documentation, and they may have known something the
repository does not show.

Before editing any file:

1. Identify which sections are generated. Generated regions are marked:

   ```
   <!-- client-docs:generated:start -->
   ...
   <!-- client-docs:generated:end -->
   ```

2. **Only edit inside those markers.** Everything outside is human-written and
   is not yours to change.
3. If a human-written statement contradicts verified implementation, **log a
   conflict and leave the text alone**. Do not correct it, do not delete it.
4. Never require a whole file to be generated. A README with one generated
   block and four hand-written sections is a normal and good outcome.

## The conflict log

Conflicts go to `docs/.client-docs-conflicts.md`. Each entry records:

- the document and section
- what the documentation claims
- what the code shows, with the file path as evidence
- the date first detected
- status: `open` or `resolved`

Rules:

- Match against existing entries. Do not append a duplicate on every run.
- Remove entries once resolved.
- Surface open conflicts as a one-line count with a path, in `/docs-status` and
  at the end of `/docs-update`.
- **Block nothing.** A conflict is information, not an error.
- This file is internal. It never appears in a generated site or any
  client-facing output.

## Answers from a human outrank inference

An answer given through `/docs-confirm` is recorded under `manually_verified`
with its date and is high confidence from then on. Never overwrite it from
inference. If the code later contradicts it, log a conflict; the human may know
something about the hosting account that the repository cannot show.

## Metadata

Generated documentation carries a small block near the top:

```
<!--
Generated by client-docs
Last audited: YYYY-MM-DD
Source: repository
-->
```

Keep it out of the way in `CLIENT-HANDOFF.md`, which a client reads. Noisy
provenance headers make a document look machine-made, which undermines the
thing you are trying to hand over.

## Write like a developer, not a brochure

Banned, along with everything of the same shape:

- "Welcome to this amazing project"
- "This comprehensive solution"
- "Leverage the power of"
- "Seamlessly integrates"
- "Robust and scalable"

Write:

> The site runs on Drupal 11 and uses Composer for dependency management.

Not:

> This cutting-edge platform leverages a robust modern architecture.

Other habits worth keeping:

- Lead with the answer. The first sentence of a section says what the thing is.
- Prefer a table when comparing things across the same columns. Prose otherwise.
- Say what a reader should do, not what they could consider doing.
- Cut every sentence that would survive being deleted.

## Say it once, in as few words as carry the meaning

Generated documentation is looked things up in, not read through. Length costs
the reader directly.

- **One sentence per idea.** If a paragraph explains the same thing twice in
  different words, delete the second.
- **No preamble.** Start with the fact. "This project uses Pantheon" beats
  "In order to understand how this project is deployed, it is worth noting
  that it uses Pantheon".
- **A table beats a paragraph** whenever the content is a list of things with
  the same shape. Three facts about each of six modules is a table.
- **Cut the reassurance.** "It is worth noting", "as you might expect",
  "simply", "of course", "please note" carry nothing.
- **Do not restate a heading in its first sentence.** The heading said it.
- **No section that only says a thing does not apply.** Leave it out.

The exception is a trap: something that has cost someone an hour, or will.
Explain that fully, including why, because the cost of it being missed is
higher than the cost of the words.

## One tab per local environment

When a project has more than one local environment committed, such as DDEV and
Lando, a reader uses one of them. Never make them read past the other.

- **Every command that differs by tool goes in tab markers**, one tool per tab,
  with DDEV first. That covers the quick start in the README, each installation
  step, verification, troubleshooting, the commands reference and any workflow
  section. The markers are `<!-- tabs:local-environment -->`,
  `<!-- tab:DDEV -->`, `<!-- tab:Lando -->` and `<!-- /tabs -->`.
- **Never write `# or` between two tools' commands**, never "run X, or Y", and
  never a table with a column per tool. A reference table becomes one table per
  tab, with the same rows in the same order.
- **Shared text stays outside the tabs.** What both tools have in common is said
  once, before the tab group. Only what differs goes inside.
- **Explanations may still compare.** A table explaining where each tool gets
  its database credentials answers "how do they differ?" and stays a table. The
  rule is for things a reader types or follows.
- **Check where each tool runs a command.** A wrapper defined in one tool's
  config may run in a set directory while the other tool's built-in runs in
  whatever directory you are in. If a command needs a `cd` under one tool, that
  tab says so.

A project with only one local environment gets no tabs.

## Make REQUIRES CONFIRMATION visible

A confirmation marker buried in a paragraph gets skimmed past, which defeats
its purpose. Where the output is rendered by a site that supports callouts,
use one.

For Starlight, that is a caution aside:

```
:::caution[Requires confirmation]
Which branch Dev builds from. The remote has both a master and a main branch
and nothing in the repository says which is authoritative.
:::
```

Three rules:

1. **The body starts with the unknown**, as a normal sentence. The title
   already says it needs confirming, so do not repeat the marker inside.
2. **A table cell cannot hold an aside.** Leave `**REQUIRES CONFIRMATION**` as
   bold text in the cell and, if the reason matters, put one aside under the
   table covering the lot.
3. **Inside a list item, indent the aside** to the item's continuation indent.
   It renders correctly. A bullet that is entirely a confirmation marker is
   better as an aside in its own right, with the bullet dropped.

Plain markdown has no aside syntax, so `:::` shows literally when the file is
read on disk or on a code host. That is an accepted cost where the site is the
destination. If a project reads its markdown mainly on a code host, use the
blockquote alert that host supports instead, and say which you chose.

## Client-facing against developer-facing

`CLIENT-HANDOFF.md` and anything in `docs/handoff-site/` is read by someone who
did not build the application. Avoid jargon where a plain word exists, explain
anything that affects what they must do, and separate what they need to act on
from what is merely true.

Developer documentation can assume the reader knows the stack. It still should
not assume they know *this* project.

## The consistency check, before you finish

For every claim you are about to write:

1. Does this exist in the code or config?
2. Is the command actually valid?
3. Does the path exist?
4. Does the environment variable exist?
5. Does the dependency exist, at that version?
6. Does the integration exist?
7. Is this safe to expose?
8. Is this client-facing or developer-facing?
9. Is it verified or inferred?

Anything that fails one of these is either corrected, labelled, or removed.
